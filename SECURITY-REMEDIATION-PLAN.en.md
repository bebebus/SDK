## 3. Remaining work

### P1: Eliminate Pinned-Dependencies findings

The five current findings come from:

- Four Codex CLI npm installation steps generated by `gh-aw` in `pull-request-reviewer.lock.yml` and `repository-maintainer.lock.yml`. Those lock files explicitly prohibit manual edits.
- One `npm install -g npm@latest` command in `release.yml` before publication.

Remediation principles:

1. Do not evade the scanner by disguising an equivalent unverified download.
2. Prefer an upstream `gh-aw` installation method with integrity verification. A repository-side alternative must use a dedicated tool directory with `package-lock.json` and `npm ci`, validate both the main Agent and Threat Detection jobs, and never hand-edit generated lock files.
3. Replace the release-time `npm@latest` upgrade with a fixed Node/npm runtime that satisfies Trusted Publishing requirements. Validate npm OIDC authentication, the idempotent version guard, and package output in a non-publishing rehearsal.

Acceptance: a new Scorecard run gives Pinned-Dependencies a score of 10, the related Code Scanning alerts close automatically, and SDK Pull Request Reviewer, SDK Repository Maintainer, and Release each have a successful validation record.

### P2: Governance and observational items

- Branch-Protection: increase required approvals or require CODEOWNERS only when the governance model needs it, not solely to raise a score.
- CII-Best-Practices: complete and maintain the project record and add its badge status to the README.
- Maintained / Contributors: let genuine maintenance history and external contributions accumulate naturally; do not manufacture commits, approvals, or contributor organizations.

## 4. Continuous acceptance

After each security-governance change:

1. Run workflow syntax and generated-lock consistency checks for every changed workflow.
2. Use a real PR to execute five-language CI and CodeQL.
3. Review open Code Scanning and Dependabot alerts.
4. Rehearse release changes without publishing; independently verify signatures and provenance after a real release.
5. Wait for a successful Scorecard run on `main`, then update this baseline from the new public API result.

Governance files, workflows, and tests do not by themselves require a new SDK package release. Changes to release artifacts must follow the existing multi-ecosystem versioning flow; published npm and PyPI versions must never be overwritten in place.
